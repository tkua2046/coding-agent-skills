# Order report performance investigation

Date: 2026-09-07. Scope: investigation only; no production or test changes.

The existing contract is `summarize(orders, catalog_path)`, which returns exact
integer-cent subtotals in input order. The catalog is fixed within a batch
([README.md](../README.md)); an empty batch currently does not access its catalog
(`tests/test_report.py`). `summarize` currently calls `load_catalog` inside the
per-order loop (`report.py`).

Baseline: `TMPDIR="$PWD" "$CANARY_PYTHON" -m unittest discover -s tests -v`
passed both existing tests (2/2, exit 0).

A bounded scratch experiment used a generated 1,000-row JSON catalog, batches of
100/1,000/5,000 orders, and five timings per implementation. It compared current
behavior with loading the same catalog once per batch. Outputs were equal at every
size. Current/once catalog-read counts were 100/1, 1,000/1, and 5,000/1; median
times were 0.033815/0.000336s, 0.354122/0.000560s, and
1.786199/0.001070s, respectively. Exact commands and stdout are in
[investigation-evidence.txt](investigation-evidence.txt).

Finding: repeated file reads and JSON decoding are sufficient to reproduce the
large-batch slowdown locally. For the 5,000-order case, eliminating repeated loads
was about 1,669x faster. A database, cache service, or job queue is not justified
by the evidence and would add operational complexity without addressing a need
established here.
