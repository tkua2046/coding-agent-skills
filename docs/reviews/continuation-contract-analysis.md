# Continuation: intake and execution-handoff contracts

**Recommendation: correct both case contracts before judging further skill repairs.** Intake should reward preserving compatibility without unnecessary questions. V6 must assess the cost of bookkeeping as well as correct delivery. Removing its exact-commit-count failure alone would leave a substantial user concern untested.

Scope: read-only inspection of these two cases, their original requests/fixtures/rubrics, and actual baseline/candidate outputs. Their live case files match the cited archived inputs byte for byte. Only this proposal was written; no model runs or result changes. The earlier experiment ceiling was our stopping policy, not a user restriction on resumed work.

## CI-01 — Intake rewards asking instead of resolving uncertainty

**Finding / consequence.** The [request](../../evals/cases/existing-intake/requests/01.md) asks for consequential questions and reversible defaults. [FEATURE.txt](../../evals/cases/existing-intake/fixture/FEATURE.txt) already requires existing behavior to remain unchanged. However, `consequential-intake` in the [rubric](../../evals/cases/existing-intake/rubric.json) specifically requires asking how error handling is preserved. This can penalize the correct, lower-effort decision to preserve the old path and its errors. It encourages another clarification round without establishing a decision that needs the user's answer.

**Observed example.** The [failed intake](../validation/canary/20260907T094757-ce99b6e7a1b7402e93107e3d2f08145a/phases/01-intake/workspace/INTAKE.md) observes `AttributeError` for `None`/integers, proposes no coercion, and retains the unchanged one-argument call as the compatibility reference. It asks meaningful customization/scope questions and exposes the pre-existing `ß` → `SS` mismatch. Its [grade](../validation/canary/20260907T094757-ce99b6e7a1b7402e93107e3d2f08145a/grade.json) fails solely for omitting an error-preservation question. The [baseline intake](../validation/canary/20260907T090136-e9f9ff66f1594c33b202c5f1e69bbf80/phases/01-intake/workspace/INTAKE.md) also lacks that question; its [grade](../validation/canary/20260907T090136-e9f9ff66f1594c33b202c5f1e69bbf80/grade.json) accepts the preservation defaults. This does not establish the reported compatibility regression.

**Smallest correction.** Version the case/rubric; keep fixture, request, actual-baseline checks and source-preservation checks. Replace the question checklist with this outcome:

> Identifies material customization decisions with examples; preserves the existing call path's observed results and failures, or identifies a concrete conflict requiring a decision. Does not assume a new customization interface, hide the failing baseline, or change legacy behavior. A preservation decision satisfies compatibility; additional questions earn no credit by themselves.

Do not require a Unicode question either when the author explicitly preserves runtime behavior and reports the contradictory test as unresolved. Ask only if a proposed change or required acceptance condition makes preservation impossible. Observing an exception alone is insufficient if the proposed next step then changes it. No intake skill patch is justified solely by this failure.

## CV-01 — V6 conflates commit count with proportionate delivery

**Finding / consequence.** [Request 06](../../evals/cases/v6-execution-handoff/requests/06.md) requires a local stage commit and recording its resulting identity. It does not require exactly one Git commit or specify where post-commit evidence belongs. The [case](../../evals/cases/v6-execution-handoff/case.json) nevertheless enforces `count == 1`. Meanwhile, all seven [semantic criteria](../../evals/cases/v6-execution-handoff/rubric.json) can pass despite excessive verification machinery. Correct behavior and useful resumption are measured; proportionate recordkeeping is inadequately measured.

**Observed example.** In [candidate 085827](../validation/canary/20260907T085827-a49cbdf9e919485186ac029e4c1b96f3/report.json), the second commit changes only PR/handoff/commit evidence. The [prior commit-count review](outcome-commit-count-review.md) establishes that narrow mismatch, but it does not establish acceptable effort:

- Code and test bytes are identical in all six phase snapshots. During phase 05, total non-skill workspace bytes grow from 47,038 to 96,701. A [41,426-byte verification record](../validation/canary/20260907T085827-a49cbdf9e919485186ac029e4c1b96f3/phases/05-resume/workspace/stage-evidence/stage-1/pr-preparation/final-verification.json) records another all-staged-file manifest and command diagnostics after verifying the existing reviewed payload. The extra preservation/index accounting dominates this new material.
- Phase 03 creates a [custom verification program](../validation/canary/20260907T085827-a49cbdf9e919485186ac029e4c1b96f3/phases/03-fix/workspace/stage-evidence/stage-1/author-recheck/verify.py) for already-correct code, encounters an import failure, and repairs its evidence formatting. The [final handoff](../validation/canary/20260907T085827-a49cbdf9e919485186ac029e4c1b96f3/phases/06-accepted-delivery/workspace/stage-evidence/stage-1/record.md) warns that rerunning this program overwrites history. Verification has created its own maintenance problem.
- Delivery adds a second commit and another hook invocation solely to record the first commit's result. That has an avoidable cost even though it is not another implementation stage. One commit containing the same excessive records would still have a proportionality problem.

These are concrete duplication/maintenance concerns, not a proposed file-size threshold. The fixture itself forces six contexts, two reviews and repeated gates: do not charge those required steps to the skill or penalize preserving original failures/reviews. Phase 05 takes 185.564 seconds and total worker time is 945.318 seconds; those include model/tool waits and do not isolate bookkeeping time.

**Smallest correction.** Version the case; retain its six-context handoff exercise, behavior oracle, gates, review/acceptance boundaries, original records and no-publication rules. Remove the raw equality check; require actual authorized delivery through the existing semantic criteria and captured phase Git snapshots: unchanged HEAD before acceptance, actual new commit afterward, intended reviewed changes, no later-stage work. A final reply may record the resulting commit/hash and hook result; the harness retains it. Do not require that identity inside its own committed document.

Add a required case-specific **proportionate-handoff** criterion, visible in the worker request: current status/evidence is sufficient for resumption; preserve originals once and link them; reuse valid reviewed-content identity; avoid new verification frameworks, redundant evidence copies/manifests and commits whose sole purpose is recording previous bookkeeping. Findings must identify the redundant operation, its consequence and a simpler way to retain the same evidence. Necessary new checks, changed-content review and the required gates remain mandatory. No universal file/line/commit quota; no generic runtime or scoring-prompt expansion.

## Controls and retest

These are proposed known-output controls, **not completed tests**. Each negative changes a decisive behavior while retaining the positive's unrelated evidence. Run them through the actual scoring path; mechanical controls still test preservation, real commits and effective gates.

| Contract | Must accept | Must reject |
|---|---|---|
| Intake compatibility | Preserve old output/errors; flag `ß` mismatch; ask only unresolved customization/scope questions. | Same note silently proposes `str(value)` or swallows legacy exceptions, despite promising compatibility. |
| Intake decisions | A genuine requirement conflict prompts one concrete question. | Generic “preserve compatibility” prose while silently choosing callback/global configuration; or blocking solely on reconfirming explicitly preserved behavior. |
| Intake baseline | Actual failing baseline retained alongside useful next decisions. | “Baseline green,” altered legacy test, or suppressed failure; extra questions cannot compensate. |
| V6 resumption | Compact current record links immutable reviews/checks and reviewed code identity; required recheck/gates run; actual local commit is identified in final reply. | Equally brief handoff with stale code identity, hidden open finding, lost original evidence, no actual commit, or commit before acceptance. |
| V6 proportionality | Retain a unique failure/review output or snapshot an otherwise unversioned prior record once. | Successful one-commit delivery with duplicated manifests, custom bookkeeping machinery and avoidable repeated verification; correctness cannot compensate. |
| V6 commit purpose | Additional work/evidence justified by a concrete changed requirement or new gate finding in an explicitly authorized control scenario. | Evidence-only follow-up solely to record the previous commit hash or prove earlier bookkeeping; renaming it “documentation” cannot excuse it. |

Review these expectations first, then run controls and fresh matched baseline/candidate trials for the two revised cases under the same execution settings. Compare both correctness and unnecessary operations; total time and file volume are observations, not automatic scores. V6 proves resumption under the supplied workflow, not that six phases are appropriate for ordinary counter changes. Preserve every original report and any new failure; a corrected measurement is not a skill improvement. Use remaining demonstrated failures to select a minimal skill repair and rerun affected cases. No controls or reruns were performed in this sidecar.
