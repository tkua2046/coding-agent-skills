## Pending decisions requiring user or stakeholder answers

All questions below are unanswered. Examples illustrate consequences; they are not acceptance criteria or selected designs.

| Question | Why the answer matters / example |
|---|---|
| What specific formatting changes must clients be able to make? Please give input/output examples. | For `" a "`, is a desired customized result `"a"`, `" A "`, `"Item: A"`, or something else? Case, whitespace, prefixes, and arbitrary transformations imply different scope; none is specified. |
| For existing callers, should the `"ß"` case preserve the current result `"SS"` or meet the test expectation `"ß"`? Is resolving that mismatch part of this feature or separate work? | Preserving runtime output leaves the current test failing; adopting the test expectation changes an observable result. The compatibility sentence and the test name do not settle that conflict. |
| Should customization affect only a selected call, subsequent calls for one client, or all clients? | If client A requests lowercase output, must a later call by A use it automatically, and must client B's unconfigured call still return `"A"` for `" a "`? The answer defines scope and isolation, without selecting an API. |
| Should customized formatting replace the existing trim-and-uppercase behavior, or retain either step; if retained, in what order? | A client seeking `" a "` with whitespace preserved cannot get it if trimming always runs first. A lowercase result becomes uppercase again if the existing uppercasing step runs last. |

Once the customization behavior is known, clarify failure handling if that behavior can fail: should an invalid customization or a failed transformation raise an error or fall back to the existing formatter? For example, fallback could silently return `"A"` when the client requested a different result. This is conditional on the selected capability, not a requirement to add callbacks or validation now.
