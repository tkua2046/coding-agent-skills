# Validation proposal: workflow behavior

Status: planned, not executed. Applies to a future implementation of [the workflow proposal](workflow-proposal.md). This file is an evaluator specification, not an implementation plan or worker prompt.

**Acceptance:** useful progress with preserved requirements, necessary design/risk coverage, maintainable artifacts, effective review and truthful evidence. Shorter output or more passing tests alone is not success.

Outline: [Reusable canary](#standardized-cases-and-grading) · [Scenarios](#trial-design) · [Evidence](#evidence-and-judgment) · [Future prompt changes](#regression-policy-for-future-prompt-changes) · [Mechanical checks](#mechanical-regression-checks).

## Standardized cases and grading

Deliver versioned evaluation assets in this repository and a runner that creates a fresh, resettable local Git fixture per run. Keep skills under test and worker inputs separate from grader-only criteria, calibration examples and historical conclusions. No separate hosted canary repo or new agent framework is required. Reuse the existing hook trial runner rather than duplicate it.

Each case has a stable ID/version, raw request and starting fixture, allowed side effects, affected skill operations/resources, environment/model settings and run budget, cost tier and predeclared criterion IDs. Expected outcomes derive from the task contract, not the candidate implementation. Port the previous intake, counter-stage and negative/positive release scenarios into this format alongside V1–V6; retain the existing eight hook outcomes and packaging tests. Map cases to the behavior they actually exercise: the old pending-review counter case does not establish a successful review/fix loop.

Use two kinds of grading, recorded separately:

- **Deterministic checks:** executable acceptance assertions, original-file preservation, commit/tag side effects, gate failures and evidence identity. Application assertions must include evaluator-owned contract checks beyond tests written by the worker. Test counts and coverage percentages are observations, not quality grades.
- **Semantic review:** a separate authorized grader context reads the requirements, produced artifacts and a versioned rubric without the author's desired verdict or the candidate's baseline/candidate label. Each criterion receives `pass`, `fail` or `inconclusive`, with a concrete evidence location and consequence. Use anchored examples for scope preservation, decision quality, actionable stages, maintainability and review closure; do not score exact headings or length alone. Calibrate the grader on known acceptable and defective outputs before relying on it. Disagreement or insufficient evidence stays visible for adjudication.

A case passes only when every required criterion passes. A required failure blocks that case's acceptance; missing or inconclusive evidence cannot pass. The tier policy below determines when the case is required for commit/PR or release. Advisory observations remain separate and cannot average away a required failure. Define retry/budget policy before execution; preserve every attempt, and never retry until a convenient green result replaces a failure. An infrastructure failure is reported as incomplete/inconclusive unless a demonstrated worker behavior itself violates the contract.

Record run ID/time, case and grader versions, raw inputs, baseline/candidate bundle and loaded-resource hashes, initial repository identity, runtime/dependency/tool versions, worker/grader model and effort settings, complete available interaction/tool records, output artifacts/diff, commands/exit codes, per-criterion judgments, elapsed time and findings/dispositions. Mark unavailable fields explicitly. Store original records immutably under `docs/validation/` with a short navigable result index; temporary workspaces/caches stay disposable. Archive failures as well as passes. No retroactive numeric grade or new-grader pass is assigned to historical trials without actually grading their available evidence and labeling that retrospective assessment.

## Trial design

Use isolated repositories with synthetic, non-interview fixtures. Record raw user inputs, starting versions, loaded skill versions, model/effort, outputs, timestamps, checks and findings. Keep evaluator expectations outside the worker's accessible inputs. Use separate author/reviewer contexts where independence is tested; an automated verdict cannot establish human acceptance.

Declare the fixture contracts and evaluation criteria before each run. Give the worker requirements, repository and selected skill operation; do not tell it the desired stage count, expected wording, known defect location or preferred verdict. If a trial times out, record incomplete work; do not count a timeout as either approval or a reliable speed benchmark.

## Evidence and judgment

Preserve unchanged skill HEAD `6573f8f422cb6528981ff43bc0d20c656096e7dc` as the initial baseline. Heavy baseline and candidate runs may be deferred and batched before release. Run both with matching inputs, grader and settings; preserve baseline failures as known failures, not successful validation, and resolve evaluation-setup blockers before interpreting comparisons. Cases may reuse completed fixture outputs where that dependency is explicit; capture their identities so a changed predecessor invalidates dependent evidence. A failed criterion requires a disposition and an affected-case rerun after correction.

Inspect semantic diffs and outcomes: missing/invented requirements, duplicated implementation detail, lost history, unjustified machinery, dependency gaps, whether a cold reader can identify next action, and whether checks/reviews apply to the current content. Require concrete counterexamples for failures; style preferences alone are not failures. Preserve original inputs/outputs and failed attempts with content hashes; summarize verdicts separately.

Record elapsed time and where available active model/tool/wait time, number of clarification/review rounds, document churn and artifacts created. These are diagnostic observations. Do not infer an Astra defect, faster model, general speedup or statistical reliability from one paired case.

## Regression policy for future prompt changes

The user's cadence is authoritative: expensive tests run before release, not on every small modification. Preserve these original clarifications: “这些重要测试应该被standardize，以及结果应该记录一下么？他们也需要被用作future skill prompt modification的safe guard吧？” and “当然太过heavy的测试也不能每次小改动都跑。在最后release之前跑就行。”

| When | Required checks / recorded status |
|---|---|
| Small edits and normal commits/PRs | Existing fast mechanical gate plus relevant lightweight regressions. Update the affected-case map and record heavy coverage as pending or tied to its previously tested version; heavy cases are not a blanket PR requirement |
| A demonstrated defect or consequential workflow change | Add/update its retained regression case. Use a targeted early agent run when it materially resolves a concrete uncertainty; no automatic full-suite run on every prompt change |
| Release candidate | Run the required heavy canary suite covering the declared behavior, alongside the final fast checks; compare with the declared baseline under matching criteria/settings. Verify evidence against the final release candidate before tagging/publication |

Map changes to entrypoints, operation prompts, templates and referenced instructions to affected operations/cases; shared/routing changes expand that map. An unmapped behavior change requires mapping/review rather than disappearing from release coverage. Ordinary research prose outside skill inputs uses fast document checks unless it changes the evaluation contract.

The machine-checked release gate verifies required case results and their association with the final candidate bundle, fixture, grader and settings. Missing, stale, failed or inconclusive required results block release, while a normal PR may explicitly defer its heavy runs. Keep the user's existing commit-hook policy. Do not confuse fast-gate success, PR readiness and release readiness. Reuse existing evidence only when its declared inputs/dependencies are unchanged and verified; after a fix during release validation, rerun affected cases instead of repeating unrelated heavy cases. Aggregate coverage must account for all required release cases and the final artifact.

Compare the candidate with the declared baseline under the same criteria. Existing baseline failures remain visible and do not grant exemptions: required acceptance must pass, and any proposed scope/criterion change needs its own justified review. Fixing a target failure must preserve the other required behaviors. Rubric changes are separately identified and reviewed; when grading semantics change, re-grade/rerun both sides as appropriate instead of comparing incompatible scores. Never lower a criterion merely to make a prompt modification pass.

Validate the safeguard itself with negative controls: a deliberately defective output must fail its grader; absent/stale release results or a changed relevant skill/grader identity must fail release readiness; a correctly bound passing control must pass. Confirm that fast PR checks can pass while heavy coverage is honestly pending. Keep these controls independent of the candidate's own tests. This proves gate mechanics and selected grading behavior, not universal model reliability.

## Mechanical regression checks

Run existing skill/resource validation, repository checker tests and the agreed pre-commit gate after implementation. Confirm copied skill bundles resolve their own resources. Verify research archives against their recorded hashes; any formatting exclusions needed to preserve original bytes require an explicit, reviewed change rather than silently rewriting sources.

V6 uses actual passing/failing local execution and content identity, not a scripted claim that tests passed. Existing hook trials remain applicable; add new hook/checker tests only if their behavior changes. Source coverage selectors, meaningful assertions and zero-test/failure propagation remain requirements, not an invented coverage percentage.

## Reporting limits

The prior 32 packaging/checker/evidence tests do not prove agent behavior. This proposal phase can verify document links, source integrity and review consistency only. Future reporting must distinguish inspected instructions, executed fixture behavior, local checks, independent review, human acceptance and remote CI/publication. Publish synthetic/redacted evidence only; keep private interview material out of this repository.
