# Validation proposal: workflow behavior

Status: planned, not executed. Applies to a future implementation of [the workflow proposal](workflow-proposal.md). This file is an evaluator specification, not an implementation plan or worker prompt.

**Acceptance:** useful progress with preserved requirements, necessary design/risk coverage, maintainable artifacts, effective review and truthful evidence. Shorter output or more passing tests alone is not success.

## Trial design

Use isolated repositories with synthetic, non-interview fixtures. Record raw user inputs, starting versions, loaded skill versions, model/effort, outputs, timestamps, checks and findings. Keep evaluator expectations outside the worker's accessible inputs. Use separate author/reviewer contexts where independence is tested; an automated verdict cannot establish human acceptance.

Declare the fixture contracts and evaluation criteria before each run. Give the worker requirements, repository and selected skill operation; do not tell it the desired stage count, expected wording, known defect location or preferred verdict. If a trial times out, record incomplete work; do not count a timeout as either approval or a reliable speed benchmark.

## Evidence and judgment

Run V1 against current HEAD `6573f8f422cb6528981ff43bc0d20c656096e7dc` and the candidate with otherwise matching settings. Run V2–V6 against the candidate; scenarios may reuse completed fixture outputs where the dependency is explicit. Do not rerun unrelated cases unless a change or finding affects them. A failed criterion requires a disposition and an affected-case rerun after correction.

Inspect semantic diffs and outcomes: missing/invented requirements, duplicated implementation detail, lost history, unjustified machinery, dependency gaps, whether a cold reader can identify next action, and whether checks/reviews apply to the current content. Require concrete counterexamples for failures; style preferences alone are not failures. Preserve original inputs/outputs and failed attempts with content hashes; summarize verdicts separately.

Record elapsed time and where available active model/tool/wait time, number of clarification/review rounds, document churn and artifacts created. These are diagnostic observations. Do not infer an Astra defect, faster model, general speedup or statistical reliability from one paired case.

## Mechanical regression checks

Run existing skill/resource validation, repository checker tests and the agreed pre-commit gate after implementation. Confirm copied skill bundles resolve their own resources. Verify research archives against their recorded hashes; any formatting exclusions needed to preserve original bytes require an explicit, reviewed change rather than silently rewriting sources.

V6 uses actual passing/failing local execution and content identity, not a scripted claim that tests passed. Existing hook trials remain applicable; add new hook/checker tests only if their behavior changes. Source coverage selectors, meaningful assertions and zero-test/failure propagation remain requirements, not an invented coverage percentage.

## Reporting limits

The prior 32 packaging/checker/evidence tests do not prove agent behavior. This proposal phase can verify document links, source integrity and review consistency only. Future reporting must distinguish inspected instructions, executed fixture behavior, local checks, independent review, human acceptance and remote CI/publication. Publish synthetic/redacted evidence only; keep private interview material out of this repository.
